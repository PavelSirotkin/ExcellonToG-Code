# Release Notes — ExcellonToG-Code v4.7

**Дата релиза:** 27 апреля 2026

---

## 🎯 Обзор релиза

Версия 4.7: Главная новая функция — **полноценное окно статистики проекта** с детальной информацией о плате, инструментах, путях и времени обработки. Также внесён ряд технических улучшений для повышения надёжности и стабильности работы приложения.

---

## ✨ Новые функции

### 📊 Полноценное окно статистики

Добавлено новое окно статистики (`ui/statistics_window.py`) с полным набором информации и визуальным оформлением:

**Информация о плате:**
- Размеры по осям X и Y (минимум, максимум, диапазон)
- Площадь платы в см²

**Информация об инструментах:**
- Сводка: количество отверстий, слотов и контура с числом инструментов
- Таблица инструментов с номером, типом (Сверло/Фреза/Контур), диаметром и количеством операций
- Раздельное отображение трёх независимых категорий: отверстия, слоты, обрезка

**Путь инструмента:**
- Быстрый ход (XY) — холостые перемещения между точками
- Рабочий ход (Z) — движения по оси Z при сверлении
- Фрезеровка слотов — длина рабочего хода при фрезеровке слотов
- Фрезеровка по контуру — длина рабочего хода при обрезке контура платы (с учётом multi-pass)
- Фрезеровка (всего) — сумма фрезеровки слотов и контура
- Общий путь — сумма всех перемещений

**Время обработки:**
- Общее время в минутах и секундах
- Детализация с прогресс-барами:
  - Быстрый ход (с процентом от общего времени)
  - Сверление (с процентом от общего времени)
  - Фрезеровка (слоты + контур, с процентом от общего времени)

**Дополнительные функции:**
- Цветовое кодирование разных типов данных
- Прогресс-бары для времени обработки
- Прокрутка для больших объёмов данных
- Кнопка копирования статистики в буфер обмена (текстовый формат)

**Исправления:**
- Окно открывается даже если загружен только контур платы (без отверстий и слотов)
- Точный расчёт длины дуг в контуре (через формулу `r·|Δθ|`)
- Учёт парковки инструмента в (0,0) после каждой группы операций
- Корректный расчёт времени фрезеровки с учётом multi-pass и Z-движений

## 🔧 Технические улучшения

### Динамический выбор номера T-инструмента для контура

**Проблема:** Номер инструмента для секции обрезки контура был жёстко зашит как `T100`. Если в Excellon-файле уже присутствует инструмент `T100`, в объединённом G-code оказывались две разные операции с одним номером.

**Решение:** Введён хелпер `_pick_outline_tool_num()`, который выбирает свободный номер:
- Если максимальный номер инструмента < 100 → используется `T100` (как раньше)
- Если `T100` уже занят → используется `T101`
- Если максимальный номер ≥ 100 → используется `max + 1`

**Файлы:** `core/gcode_generator.py`, `ui/app.py`  
**Тесты:** 8 новых тестов

---

### Защита от зависания на вырожденных входах в multi-pass

**Проблема:** Функция `_calc_multipass_offsets` использовала цикл `while True` без защиты. При `tool_diameter <= 0` или `slot_width <= 0` возникал бесконечный цикл — GUI зависал без возможности отмены.

**Решение:** Введены три уровня защиты:
1. Валидация входов (возврат `[]` при некорректных значениях)
2. Жёсткий потолок итераций `_MULTIPASS_MAX_ITER = 10000`
3. Защита `_write_slot_passes` от пустого `offsets` с комментарием в G-code

**Файлы:** `core/gcode_generator.py`  
**Тесты:** 9 новых тестов

---

### Рефакторинг Z-движений в общие хелперы

**Проблема:** Логика генерации G-code для Z-движений была дублирована между несколькими функциями, что приводило к риску несогласованности формата вывода.

**Решение:** Вынесены низкоуровневые хелперы вывода G-code:
- `emit_rapid_xy(buf, x, y, rapid_rate)` — холостое перемещение XY (G00)
- `emit_mill_xy(buf, x, y, mill_rate)` — рабочее перемещение XY (G01)
- `emit_plunge_z(buf, z, plunge_rate)` — погружение по Z (G01)
- `emit_retract_z(buf, z, rapid_rate)` — подъём по Z (G00)

Это гарантирует единообразный формат вывода (X/Y в `.3f`, Z в `.2f`, подача в `.0f`).

**Файлы:** `core/gcode_generator.py`, `core/outline_gcode.py`

---

### Валидация замкнутости контуров

**Проблема:** Функции `offset_segments` и `insert_tabs` предполагали, что входной контур замкнут, но не проверяли это условие. На незамкнутом контуре создавался некорректный offset с разрывом.

**Решение:** Добавлена функция `is_closed_contour(segments, tol_mm=1e-3)`, которая проверяет замкнутость контура. Функции `offset_segments` и `insert_tabs` теперь возвращают `[]` для незамкнутых контуров.

**Файлы:** `core/polygon_ops.py`  
**Тесты:** 10 новых тестов

---

### Ограничение итераций в TSP-оптимизации

**Проблема:** Функции `two_opt` и `two_opt_slots` использовали цикл `while improved` без ограничения. На больших платах (1000+ отверстий) GUI мог зависнуть на десятки секунд.

**Решение:** Добавлено ограничение числа итераций:
- Константа `_TWO_OPT_MAX_ITERATIONS = 1000`
- Параметр `max_iterations` в функциях `two_opt` и `two_opt_slots`
- Опциональный параметр `time_budget_ms` для ограничения по времени

На типичных платах (100-500 отверстий) алгоритм сходится за 10-50 итераций — лимит не срабатывает. Для больших плат лимит предотвращает зависание.

**Файлы:** `core/tsp_optimizer.py`  
**Тесты:** 7 новых тестов

---

### Улучшенная обработка ошибок парсинга

**Проблема:** Функции `parse_excellon_file` и `parse_slot_file` использовали `map(int, coord_format.split('.'))` без обработки ошибок. На повреждённом формате координат выбрасывался технический traceback без объяснения причины.

**Решение:** Добавлена явная обработка ошибок с понятными сообщениями на русском языке:
```
Неверный формат координат '<value>'. Ожидается N.N (например, '3.3' или '4.2'). Подробности: <original error>
```

**Файлы:** `core/parser.py`  
**Тесты:** 7 новых тестов

---

### Исправление формирования перемычек (tabs) при multi-pass

**Проблема:** При фрезеровке контура в несколько проходов перемычки (tabs) формировались только на последнем проходе. Это приводило к тому, что итоговая высота перемычки была равна `depth_per_pass`, а не заданному параметру `tab_height`.

**Решение:** Изменена логика определения начала формирования tabs:
```python
tab_start_z = drill_z + tab_height
should_use_tabs = (n_tabs > 0 and current_z <= tab_start_z)
```

Теперь tabs начинают формироваться на том проходе, где фреза достигает уровня `drill_z + tab_height`.

**Файлы:** `core/outline_gcode.py`  
**Тесты:** 1 новый тест

---

### Точная длина дуги в статистике

**Проблема:** Длина дуги аппроксимировалась как `chord_length * 1.2`, что давало погрешность до 30% для полукруга.

**Решение:** В `core/polygon_ops.py` выделена публичная функция `segment_length(seg)`, которая точно считает длину одного сегмента (евклидова для линии, `r·|Δθ|` для дуги). Статистика теперь использует точные значения.

**Файлы:** `core/polygon_ops.py`, `ui/statistics_window.py`

---

### Учёт парковки в статистике

**Проблема:** При расчёте `total_rapid` не учитывался возврат в (0,0) при парковке после каждого инструмента.

**Решение:** В `calculate_paths()` для каждой группы операций после прохода добавляется `last_pos → (0,0)` — соответствует фактической парковке в G-code.

**Файлы:** `ui/statistics_window.py`

---

### Улучшения логирования

**Проблема:** `ui/statistics_window.py` писал `print(...)` напрямую в stdout. В Windows-сборке без консоли пользователь этого не видит.

**Решение:** Добавлен `import logging; logger = logging.getLogger(__name__)`. Все диагностические сообщения теперь идут через `logger.warning(...)`.

**Файлы:** `ui/statistics_window.py`

## 📋 Известные ограничения

- **Gerber**: поддержано минимальное подмножество RS-274X, достаточное для outline-файлов
- **Offset внешних углов**: простое пересечение смещённых рёбер (острые углы остаются острыми)
- **TSP 2-opt**: жадный эвристический алгоритм, не гарантирует глобального оптимума
